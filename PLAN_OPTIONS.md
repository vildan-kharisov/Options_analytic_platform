## 1) Этап MVP (стабильный аналитический дашборд)

Цель: довести текущую версию до устойчивого ежедневного использования трейдером по 4 активам.

### 1.1 Данные и SQL-слой
1. Применить SQL-скрипты:
   - `sql/portfolio_schema.sql`
   - `sql/views_market_inputs.sql`
2. Проверить consistency таблиц:
   - ключевой маппинг `market_history.asset` ↔ `asset_code`.
3. Вынести SQL-запросы для текущих графиков в отдельный слой (файлы в `sql/` + загрузка из Python), чтобы не держать SQL строками внутри обработчиков.
4. Добавить в API endpoint health-check (`/api/health`) и endpoint версии (`/api/version`).

### 1.2 API (Flask)
1. Стандартизировать ответы API:
   - единый формат: `{"ok": true/false, "data": ..., "meta": ..., "error": ...}`.
2. Для каждой группы графиков сделать отдельные endpoint:
   - OHLC + `exp_std` bands
   - HV/IV (включая next-month IV)
   - Smile / multi-series smile
   - Term structure
   - Greeks (Delta/Gamma/Vega/Theta)
3. Добавить валидацию входных параметров:
   - `asset` только из допустимого списка
   - безопасные значения `date`, `series`, `rows`.
4. Убрать дубли логики выбора «последней даты» в централизованные функции.

### 1.3 Frontend (ECharts)
1. Разбить монолитный JS внутри `echarts_dashboard.html` на модули:
   - API-клиент
   - состояние фильтров
   - рендереры графиков
2. Привести вкладки `SI/RTS/GOLD/BRENT` к единому шаблону (чтобы не дублировать код под каждый актив).
3. Завершить базовый функционал рисования:
   - добавление линии
   - очистка
   - сохранение состояния линий при refresh текущей вкладки.
4. Улучшить UX:
   - индикатор загрузки,
   - fallback «нет данных»,
   - отображение даты среза данных на каждом графике.

### 1.4 Критерии готовности этапа MVP
- Все графики из `PROJECT.md` стабильно открываются для 4 активов.
- API не падает при пустых данных/ошибке источника.
- Обновление данных из ETL отражается в UI без ручных правок.
- Пользователь может запускать/останавливать приложение по `INSTRUCTION.md`.

## 2) Этап MVP+ (расширенная аналитика волатильности)

Цель: добавить практичные сигналы для торговых решений (что уже зафиксировано в `PROJECT.md`).

### 2.1 Новые метрики и графики
1. `IV Rank / IV Percentile (252d)` по активу и серии.
2. `IV - HV` spread + `Z-score`.
3. `Skew`: `IV(put_25Δ) - IV(call_25Δ)` по времени.
4. `Term Structure Heatmap` (Date × DTE × IV).
5. `Smile evolution` (слайдер/анимация по датам).
6. `Open Interest by Strike + ΔOI + PCR`.

### 2.2 Источник OI
1. Реализовать модуль загрузки OI:
   - Приоритет 1: ISS API (структурированные поля OI).
   - Приоритет 2: fallback-парсер страниц MOEX (если в ISS нет нужных полей).
2. Создать таблицу `option_oi_history`:
   - `asset_code`, `optionseries_code`, `strike`, `opt_type`, `oi`, `oi_change`, `date`.
3. Добавить DAG для OI.

### 2.3 Критерии готовности этапа MVP+
- Все 6 доп.графиков доступны на 4 вкладках.
- OI-данные загружаются минимум раз в торговый день.
- Для каждой метрики есть описание формулы в документации.

## 3) Этап Portfolio Lab v1 (конструктор и оценка портфеля)

Цель: перейти от аналитики к прикладному моделированию опционных стратегий.

### 3.1 Backend API
1. Реализовать CRUD endpoints из `PORTFOLIO_LAB_API_SCHEMA.md`:
   - `POST/GET/PATCH/DELETE /api/v1/portfolios`
   - `POST/GET/PATCH/DELETE /api/v1/portfolios/{id}/legs`
2. Реализовать:
   - `POST /api/v1/portfolios/{id}/valuate`
   - `POST /api/v1/portfolios/{id}/scenarios/run`

3. Подключить `sql/queries_portfolio.sql` как основной SQL-слой.

### 3.2 Расчетная логика
1. Ценообразование ноги:
   - приоритет: `mid -> theoretical -> entry_price`.
2. Агрегация Greeks на портфельном уровне:
   - учитывая `BUY/SELL`, `qty`, `lot_size`.
3. Расчет payoff на экспирацию и сетки сценариев (spot shift × vol shift).
4. Запись результатов:
   - `portfolio_snapshot`
   - `scenario_run`.

### 3.3 UI Portfolio Lab
1. Добавить отдельный блок/вкладку `Portfolio Lab`:
   - список портфелей,
   - таблица ног,
   - кнопка переоценки.
2. Графики:
   - payoff,
   - scenario heatmap,
   - агрегированные Greeks.
3. Экспорт/импорт стратегии (JSON).

### 3.4 Критерии готовности этапа v1
- Пользователь создает портфель через UI.
- Добавляет/удаляет ноги.
- Получает текущую оценку и сценарную карту.
- Результаты сохраняются в БД.

## 4) Этап Production Ready (надежность и сопровождение)

Цель: сделать систему устойчивой в эксплуатации.

### 4.1 Надежность
1. Логирование API и ETL в едином формате.
2. Retry/timeout/circuit-breaker для внешних запросов MOEX.
3. Алёрты по сбоям DAG (Airflow notifications).
4. Контроль качества данных (data checks):
   - пропуски по активам/датам,
   - аномальные значения IV/HV.

### 4.2 Производительность
1. Индексы по часто используемым фильтрам:
   - `asset_code`, `today`, `expiration_date`, `optionseries_code`, `strike`.
2. Кэш для тяжелых endpoint (`Redis`, опционально).
3. Предрасчет витрин для heatmap/skew/rank (materialized views).

### 4.3 Тестирование
1. Unit-тесты SQL и API.
2. Интеграционные тесты (API ↔ БД ↔ ETL output).
3. Smoke-тест после каждого обновления ETL.

### 4.4 Критерии готовности этапа Production Ready
- Перезапуск системы без ручной отладки.
- Прозрачные логи и алёрты по ошибкам.
- При увеличении объема истории время ответа остается приемлемым.
